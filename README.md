# axon

ローカルで動く個人用のタスク管理ツール。コーディングエージェントが主要な利用者。

**まだ実装されていない。** 現在は設計が固まった段階で、`docs/` に設計の記録がある。

## 何を解こうとしているか

既存のローカル issue tracker (br / beads_rust) を使ううちに溜まった不満が出発点になっている。
中心にあるのは、**`status` という単一フィールドに性質の異なる概念が畳まれている**こと。

- 作業の進行 (open / in_progress / closed)
- 可視性の操作 (deferred / draft)
- 表示上の強調 (pinned)
- 依存グラフから導出できるはずの値 (blocked)

単一フィールドなので値は排他になり、着手中の issue を後回しにすると進行状態が消える、
後回しを解除すると元の状態に戻らない、といった破壊が起きる。
さらに「やると決めたか」を表す軸が無いため、思いついたものを投げ込むと
「次にやること」の一覧が汚れる。

axon はこれを**軸の分解**で解く。

## 設計の骨格

保存するのは 3 つの状態と 2 種類の関係だけ。

| | 内容 |
| --- | --- |
| A 進行 | 未着手 / 着手中 / 終了 |
| B 採否 | 未判断 / 採用 / 不採用 |
| C 時期 | いつ再び意識に上げるか (条件。null なら常に浮上) |
| 依存 | issue 間 (前提の 1 種類のみ) |
| グループ | 機能群。階層を持ち、グループ間にも依存を張れる |

`ready` / `blocked` / `orphaned` / 進捗は**すべて導出値**で、テーブルに持たない。
優先度と表示は**持たない**。

軸が直交しているので、要らない軸だけを落としても他が壊れない。
優先度を持たない判断はこの性質の上に成り立っている。

## 名前

`axon` は軸索。`axis` (軸) と同語源で、**軸を分解したことが設計の核心**であることによる。
軸索が信号を一方向に伝えるのは、依存グラフの伝播とも重なる。

## 適用範囲

**個人のタスク分解・管理に絞る。** プロダクト全体の ITS としては使わない。

両者は要件が違う (共有の要否、PR からの参照、保存形式の制約) ため、
混ぜると設計が引きずられる。プロダクト用途が必要なら別のツールを使う。
