# 新しい lifecycle を土台に Axon を作り直す

## 起点

> メインリポジトリに現行の実装残ってるから、このgit worktreeのコードは全部消しちゃっても問題ないくらいの気持ちなんだけど、どう進めるのが良いかな？
>
> 主導してもらって良い？
>
> file backend, sql backend両方必要です。初回の実装ではsql backendだけでもいいけど、file backendのために大きな設計変更が必要になる状態は避けたいです。

## 確定済み設計

### 問題と成功条件

旧 Progress・Disposition を単一の lifecycle へ置き換え、実際に運用できる新しい Axon を作る。仕様の正本は [lifecycle_proposal.md](../../spec/lifecycle_proposal.md) である。以下の要約と正本が食い違う場合は正本を確認する。

未判断の改善案を記録でき、採用済みの仕事を実行でき、Group で計画を構成できることが目的である。登録、取得、採否、着手・終了、文面編集、所属・依存の変更、候補の確認、Note と履歴の参照が一巡し、SQLite と file の両方で同じ通常操作の意味を持つことを完成条件とする。SQLite の先行利用は中間成果であり、両 backend の完成とは区別する。

### Scope と制約

- Issue・Group の五状態と七操作、提案・採用済みの登録を実装する。通常操作で完了は戻さない。
- 入れ子 Group、一親の包含、所属変更、全 Entity 種別間の dependency、両者を合わせた通常完了経路の循環拒否を実装する。
- 再浮上条件は未設定か外部コマンド一つ。`triage` と `tasks` を専用一覧とし、`list` を全状態の絞り込みに使う。`tasks` は浮上した未着手（依存待ち・親の着手待ちを含む）と全着手中を表示する。明示的な変更操作は条件コマンドを評価しない。
- 文面の編集範囲、追記専用 Note、自動状態変更履歴、任意の記録者情報と自動取得を実装する。
- SQLite と file を共通のコアへ接続する。file の分岐・統合に必要な記録モデルを最初から両 backend に適用する。
- 旧 CLI・データ形式・既存機能との互換性、自動データ移行を要求しない。メインリポジトリの旧実装と実データを変更せず、この worktree の実装を置き換える。
- 一括編集・宣言ファイル import/export は今回の完成条件に含めない。意図・目的は spec に残してある。file snapshot の保存・統合はこれと別の機能である。
- claim、旧 Revision、採用時の全文保存、文面の編集履歴、組み込み日時・Manual・AfterEntity を復活させない。

### 方針と trade-off

Rust と現在のビルド・検証基盤を使う。旧コードとの並存や互換層を完成形に残さず、使える低レベル処理だけを取り出す。通常操作の判定・適用・履歴生成を SQL やファイル I/O から分離し、一つの実装へ集約する。

Entity の現在値と、不変な記録の集合・先行関係を分ける。記録には生成時から安定 ID を付け、SQLite の row ID や時刻を公開参照・分岐間の順序に使わない。統合で両側の履歴・Note を保持し、選択結果を通常遷移とは別の統合記録で説明する。SQLite 先行の段階でも、この情報を失わず保存・取得できるようにする。

通常操作と merge の全体検査は、共通の状態・包含・依存の規則を使う。統合で入力から選ぶ行為を通常遷移の guard だけで判定することも、統合という理由で構造の制約を外すこともしない。形式モデルを全実装へ拡張することはせず、分岐・統合の新しい相互作用を必要な範囲で検証する。

### User 可視の振る舞い

各通常変更は最新の保存状態を基準に原子的に判定・保存し、拒否時に状態や履歴を部分変更しない。SQLite の共有保存先では同一 Entity の並行 start の一方だけが成功する。file の独立した worktree 間では保存状態も分岐するため、共有 SQLite と同じ全 worktree 排他を提供する前提にしない。

分岐した片側が Completed、他方が NotStarted なら、統合時には未完了側を明示採用してよい。両側の実際の操作を保持し、採用結果を記録する。通常の Completed からの再開操作は追加しない。

Group の完了は、子の終了と依存先の完了だけで自動実行しない。最終確認が通ったことを呼び出し側が明示的に伝える入口を設ける。ツールが外部の実装成果を自動審査する機能にはしない。

候補一覧の必要な条件評価が失敗したら、一覧全体が失敗する。成功した一部の候補を成功結果として返さない。保存済みの情報を取得する経路と、条件を評価して候補を求める経路を分離する。

### CLI と表示の確定事項

公開コマンドと表示契約は spec の「CLI と表示」に従う。`triage / tasks / list`、`show`、`note list|add`、`log`、`capture / plan / group capture / group plan`、`accept / withdraw / start / release / done / cancel / reconsider`、`write`、`group set A --parent G / group unset A`、`dep add|rm A --needs B`、`when set A --command … / when clear A` を基本構成とする。

一覧は `ID / 種別 / 状況 / タイトル`、作成日時の古い順で統一する。状況は未判断・着手可能・依存待ち・着手中・着手中かつ依存待ち・完了・取りやめを区別する。`show` は ID を先頭に本文と短い補助情報、必要な直接の待ち理由を表示する。Group だけ末尾へ直属の子と終了数を加える。Note は件数だけを示し本文は別入口、履歴は `log`、内部の causal 情報・コマンド案内・重複した依存列挙を通常表示へ足さない。

Group の `done` 自体を最終確認済みの明示入力とし、別フラグや状態は追加しない。確認手順は利用側の skill に置く。全子孫の Note の一括取得は初回必須にしない。

### 確認根拠

設計の経緯・検証範囲は `spec/lifecycle_proposal.md` にある。2026-09-11 の会話で、既存互換・自動移行が不要、この worktree を作り替えてよい、机上検討を続けるより運用可能な実装へ進む、両 backend が必要、SQLite 先行でも file のための大幅な設計変更を残さない、という方針が示された。両側の履歴を保持する統合方針と、統合時に未完了側を明示採用する提案も了承された。

## 調べたこと

2026-09-11、旧実装が残る `7d62fc9` と現在の検討 spec を確認した。以下の旧資料は比較材料であり、新 lifecycle の仕様を上書きしない。

- `src/core.rs` / `src/storage.rs` / `src/db.rs`: 現行も状態操作と保存 adapter を分離している。ただし core の snapshot は旧 Revision・claim・因果情報を含み、そのまま新モデルには使えない。
- `docs/design/file-backend.md` / `docs/development/branch-history.md`: file 導入は安定 ID、因果関係、統合記録、現在値の根拠を共通モデルへ追加した。SQL の抽象化だけを先に作っても、分岐への備えにはならない。
- `src/history.rs` / `src/merge.rs`: 両側の記録の保持、ID 衝突の拒否、現在値の選択、候補全体の検証がある。旧 Revision の再利用や claim の結合は今回移植しない。
- `docs/reference/file-storage.md`: worktree 内での file 保存、安定した lock ファイル、atomic replace と同期、結果不明、入力の変化検知、Git index の未解決拒否を扱う。保存・統合の安全性を理由なく緩めないための参照先とする。
- `src/derived.rs` / `tests/integration/command.rs`: process group、timeout、中断、上限付き出力取得の実装と試験がある。実行処理は再利用候補だが、旧 ready/show/start の評価対象やキャッシュの配置は新規則に置き換える。
- `src/display.rs` / `src/actor.rs`: 端末制御文字の表示処理は再利用候補。actor は現在文字列だけを返すため、session 情報を扱う独立した連携へ変更する。
- `spec/lifecycle_proposal.md` の情報モデルは単一の履歴列を検証している。merge を含む状態へそのまま `invHistoryExplainsCurrentState` を適用することはできない。
- `Cargo.toml` / `rust-toolchain.toml` / `.github/workflows/full-verification.yml` / `lefthook.yml`: Rust、fmt、Clippy、test の基盤がある。crate を分ける場合は pre-commit が library 側のテストを取りこぼさないように更新する。
- `scripts/build-canonical-axon` は linked worktree では共有 binary を更新しない。ローカル設定が旧 binary を PATH に入れることがあるので、新実装の確認は明示したローカル binary と独立 fixture で行う。
- `.axon/state.jsonl` は tracked な実データである。「旧コードの撤去」の対象に含めない。

## 置き換えと再利用の境界

残す土台は Git 履歴、`LICENSE`、新しい literate spec、Rust の toolchain とビルド・検証基盤である。`AGENTS.md` と docs の入口は、新旧どちらが実装の規範か曖昧にならないよう更新する。

旧 `src/domain.rs`、状態操作・導出、DB schema、codec、履歴、merge、declaration、CLI は新しい構成へ置き換える。低レベルの ID 発行、端末表示、process 監督、保存原子性の処理は契約が一致する範囲で移植できる。旧実装の全文コピーを予備として保存する必要はない。Git 履歴から参照する。

旧 `spec/*.qnt`、利用ガイド・契約、同梱 docs、plugin/skill、旧意味を要求する tests は、新機能に対応したものへ置き換えるか、過去資料であることを参照元も含めて明示する。不要な旧 CLI をテストのために残さない。旧テストに含まれる並行書込、障害、端末、process の検証目的は、新しい操作へ適応して維持する。

撤去は以下の成果を作る変更と対応させる。先に全ファイルを削除して長期間ビルド不能にする工程は設けない。実データ、ローカル設定、メインリポジトリ、インストール済み plugin をこの撤去に巻き込まない。

## 作業の塊

### 1. 分岐を保持できる共通コアと保存表現

- 成果: SQL に依存しない Entity・操作・Note・状態履歴・統合記録と、両 backend が保持する論理 snapshot。通常操作と分岐の両方をメモリ上で扱える。
- 完了条件: 基本遷移と情報の編集制約を検査できる。独立した同内容 Note が別 ID で保持される。同じ祖先から start→complete と start→release に分かれた履歴を両方保持し、未完了側の明示選択と、その後の通常操作を説明できる。日時の逆転や同一時刻で因果関係を変えない。重複 ID の異内容・参照切れを拒否する。共通 snapshot を canonical な file 表現へ往復して情報を失わない。SQLite の保存列を固める前に、この縦断ケースを通す。
- 前提: なし。
- 由来: 両 backend を必要とし、file 導入時の大幅なモデル変更を避ける判断。

### 2. Group・dependency を含む通常操作の完成

- 成果: 共通コアが登録・包含・依存・状態変更を一体で検査する。固定数の探索モデルを、動的な Entity 集合へ実装する。
- 完了条件: 親を自動着手しない、進行中の子がいる親を解放できない、未判断の子が Group 終了を妨げる、最終確認なしでは Group 完了できない、未完了の依存先が着手・完了を妨げる、着手中への依存追加は状態を変えない、完了後の依存固定と終了した親の構成固定を満たす。親子間・複数階層・別計画をまたぐ前提循環を登録・所属変更・依存追加で拒否する。取りやめ・完了を循環検査から除外しない。拒否した変更が記録を残さず元状態を保つ。
- 前提: 1 の共通 snapshot と通常操作境界。
- 由来: 統合モデルで合意した状態・包含・依存の相互作用。

### 3. SQLite で登録から記録参照まで利用できる入口

- 成果: 共通モデルを失わず保存する SQLite adapter と、初期化・登録・取得・変更・Note・履歴を使う CLI。公開コマンド名と `show`・子一覧・Note・`log` の通常表示は合意済み契約へ合わせる。ここで旧 CLI・旧 schema への依存を外す。
- 完了条件: 新しい独立した保存先で登録から Group 完了まで通る。状態変更と履歴保存が一 transaction で確定する。並行 start の一方のみが成功し、別 Entity の並行操作・Note 追加を失わない。SQL に通常操作の意味を複製せず、共通コアの失敗を伝える。メモリ上で作った分岐・統合済み snapshot も SQLite へ保存・再読取して保持できる。未知・旧 schema を暗黙変換しない。保存失敗と出力失敗を区別する。
- 前提: 1 と 2 の完了条件。
- 由来: SQLite を先行利用できる区切りと、file でも同じ情報モデルを使う制約。

### 4. 候補一覧と外部コマンドの評価

- 成果: `triage`・`tasks`・`list` を役割どおりに取得し、`when set|clear` で条件を設定・修復できる。
- 完了条件: `tasks` が依存待ち・親の着手待ちの未着手を浮上判定から除外しない。着手中は浮上を問わず含め、その条件は子孫の判定に必要な場合だけ評価する。`triage`・`tasks` は表示対象の状態と祖先だけを必要な範囲で評価し、`list` は評価しない。必要な祖先を上から評価し、未成立の配下を省略する。一 invocation で同じ Entity は最大一回、次回は再評価する。必要な判定失敗で部分的な成功一覧を返さない。明示的な状態変更・条件設定は shell を起動しない。既定30秒、終了0/1/その他、Ctrl-C、子 process、出力上限、trace 書込失敗を実 process で検査する。
- 前提: 2 の構造判定と 3 の保存・CLI 入口。
- 由来: 再浮上を状態から分離した候補一覧の契約。

### 5. 記録者情報の自動取得と初回運用の案内

- 成果: 独立した Rust crate の連携で取得可能な actor/session 情報を記録し、新 CLI の利用案内・skill とともに SQLite で一巡できる。
- 完了条件: 通常のコマンド呼出しで取得可能な情報を補完でき、取得不能でも操作が失敗しない。core は特定エージェントの必須 schema・環境検出・権限判断を持たない。記録者の詳細を再取得できる。利用ガイド・help・skill に旧状態、claim、Revision、一括編集の必須手順が残らず、新 binary の選択と手動データ持込みの境界が分かる。
- 前提: 3 と 4 の利用可能な入口。
- 由来: セッションをたどるための付随情報と、早期に実運用へ進む目的。

### 6. 分岐した計画の安全な統合 engine

- 成果: base・両側の snapshot を受け取り、記録を保持し、現在値の選択と候補全体の検証を行う backend 非依存の engine。
- 完了条件: 別 Entity の変更と独立した Note を失わない。同一 Entity の異なる現在値を黙って合成しない。片側が完了した競合で未完了側を明示採用でき、通常の再開イベントを捏造しない。各側では有効だった依存を合わせた循環、終了した Group への子の流入・構成変更を検出する。選択した終了状態とその構成の対応を確認する。同一記録の異内容を拒否する。再統合で記録が増殖しない。統合の検査・修正で外部条件コマンドを実行しない。
- 前提: 1 の分岐表現と 2 の通常操作・構造検査。SQLite 先行利用に先立って、1 の最小統合ケースはすでに通っていること。
- 由来: 分岐を事実のまま保持し、統合時の判断と通常遷移を区別する合意。

### 7. file 保存と worktree・Git 統合

- 成果: 同じ通常操作を現在の worktree 内で実行する file adapter と、安全な統合結果の公開・Git への接続。
- 完了条件: worktree A の通常操作で main/B の正本が変わらず、取り込み後だけ状態が伝搬する。同一 worktree の writer は lock 下で最新状態を読み、完全な snapshot だけを公開する。置換前失敗・置換後の結果不明を区別する。統合入力・保存先の変更、未解決の Git index、壊れた入力で正本を部分変更しない。Git が engine を呼ばない経路も通常読取の検査で扱う。SQLite と同一の ID・時刻・操作入力を与え、状態・全記録・失敗が一致する。file 対応のために 1 の意味や 3 の情報を作り直さず接続できる。
- 前提: 3 の CLI/adapter 境界、4 の評価、6 の検証済み engine。
- 由来: 両 backend の必要性と、現行 file 運用で得た保存・分岐の要件。

### 8. 両 backend での運用導線と旧仕様の撤去完了

- 成果: 新しい Axon を選んで導入・日常利用でき、旧仕様が混在しない repository。
- 完了条件: 両 backend の登録・候補選択・並行作業・Note・Group 最終確認を独立 fixture で一巡する。file では実 Git worktree の分岐・競合・解決まで通す。文書・同梱 skill・help・CI の参照を整合させる。fmt、Clippy、全テストが通る。新しい実装で実データを使う場合は利用者が対象と持込み内容を選び、旧データへの書込みや自動切替を行わない。
- 前提: 5 と 7 の完了条件。
- 由来: 運用から次の不足を見つけられる完成状態。

## 実装時の検証と判断の境界

Quint の通常操作モデルは対応する Rust の契約テストの根拠にする。探索の Entity 件数上限は実装へ持ち込まない。分岐・統合と通常遷移の区別など、新しい相互作用の検証が必要なら焦点を絞った補助モデルを作る。既存の完了固定 invariant を単に削って merge を通す対応はしない。モデル変更は型検査と関連する simulation、Rust は通常の fmt・Clippy・test および保存・process の試験で確認する。

合意した CLI 名・役割・表示要素を維持し、残る細かな option・配置、SQL の配置、Rust の module 分割などは、上の振る舞いを変えない実装設計として agent が進める。公開契約として説明してから実装へ接続する。merge の自動解決範囲や履歴の保持、Group の終了制約を変える必要が判明した場合は、実装都合として処理せず、その具体例に絞ってユーザーへ戻す。

このファイルは進捗の正本にしない。再開時は最新の会話、spec、コード、テストを照合し、各塊の完了条件がすでに満たされていないか確認する。
