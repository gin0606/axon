# 実装方針

## 言語: Rust

**要件**: 状態遷移の規約を型で表現し、規約違反 (実装ミス) をコンパイル時に検出できること。

この要件で **Go は落ちる**。直和型がないため C の条件 (`Always | AtDate | AfterEntity`) を型で表現できず、interface と型スイッチで代用しても網羅性チェックが効かない。条件を 1 つ足したときの対応漏れをコンパイラが検出できない。

TypeScript は判別可能な union と `never` を使った exhaustive check で近いことはできるが、実行時の保証がなく、branded type も型注釈を外せば通る。

Rust を選んだ理由:

| 表現したいこと | 手段 |
| --- | --- |
| A / B / C が取りうる値の限定 | `enum` |
| 条件を足したときの対応漏れ検出 | `match` の網羅性検査 |
| Issue / Group 共通 ID と文字列を取り違えない | `EntityId` newtype |
| claim は着手中のときだけ | 遷移関数の引数型で制約 |
| DB から読んだ値が想定外なら落とす | `TryFrom` による境界での検査 |

`spec/axon.qnt` の sum type がそのまま Rust の `enum` に対応するため、仕様と実装の距離が近い。最後の項目は「境界で validate、内部は信頼」の方針にあたる。DB から読んだ Entity の値を型に変換する境界は `RawEntity::into_entity` に集約し、別の読み出し経路に変換・検査を分散させない。この境界を通った内部の値は型を信頼する。

**懸念**: 変更コストが高いこと。ただしモデルを先に固めてあるため、後から変わるのは主に CLI の表層で、そこは Rust でも変更コストが低い。

## 段階的に入れた判断

最初から全部作らず、後から足せるものは落として始めた。そのとき「落とすための条件」を先に決めたものがあり、これが後で効いた。

- **履歴を後回しにする条件は「状態更新の経路を 1 箇所に集約しておく」こと** だった。集約されていたため、後から `Store::apply` にログ出力を挟むだけで足りた。更新経路が散らばっていたら、記録漏れを探して回ることになっていた
- **`blocking cause` は依存が深くなってから足す**と決めていた。Quint での検査で「無いと阻害の原因が説明できない」と分かっていたが、初期は issue 数が少なく目で追えるため
- **claim の全件確認は頻度が低いので後回し**にした。重複着手は `start` の条件付き更新で防げており、残るのは「現在誰がどこで着手しているか」を整理する経路だけだったため

## スコープの決め方

「まず持たずに始めて、実際に困ってから足す」で通している。持たない判断をしても他が壊れないのは、軸が直交しているため (`axes.md` 参照)。

判断を保留したものは axon の issue に未判断として入れてある。未判断のものは `axon ready` に出ないため、作業候補を汚さない。

## CLI の決め方

紙の上で詰めず、実装しながら決める。コマンド名や出力は実際に打つと必ず変わるうえ、間違えてもデータ移行が要らないため。
