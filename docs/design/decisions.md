# 設計判断

現在の契約そのものは [lifecycleと構造の契約](../reference/lifecycle.md)、[候補と外部条件](../reference/candidates.md)、[CLIと表示の契約](../reference/cli.md)、`docs/reference/` と `docs/development/` の各文書が定義する。この文書は、それらがなぜその形になっているかを残す。契約と矛盾する記述を見つけた場合は契約側を正とする。

## 保存する要素を性質で分ける

Axon が Entity ごとに保存するものは、性質の違う三種類に分かれる。

| 種類 | 保存されるもの | 例 |
| --- | --- | --- |
| 利用者が明示的に遷移させる状態 | 一つの lifecycle と、その変更履歴 | `Undecided`・`NotStarted`・`InProgress`・`Completed`・`Cancelled` |
| Entity 間の関係 | 親 Group の ID、outgoing dependency の ID 集合 | 包含、dependency |
| 機械が判定する属性 | 外部コマンドの文字列 | 再浮上条件 |

一覧の状況 (Ready、Blocked) と候補集合は、これらから完全に導出する。優先度と表示上の強調は保存しない。

この分け方は、性質の違う値を一つのフィールドへ畳むと操作どうしが互いを壊すことへの対処である。Axon は、個人向けの issue tracker である beads_rust を長く使ってきたところから始まっている。長く使うほど自分の手に合わせたい部分がはっきりし、その要求を形にしたものが Axon の出発点になった。

beads_rust は `status` という単一フィールドに、進行 (`open`・`in_progress`・`closed`)、依存から導出できる `blocked`、可視性の操作 (`deferred`)、成熟度 (`draft`)、表示上の強調 (`pinned`)、削除の記録 (`tombstone`) を並べる形を取る。性質の違うこれらを一つのフィールドに載せると値どうしが排他になり、ある意味づけの操作が別の意味の値を上書きしうる。表示上の強調を付けた時点で進行の値が置き換わる、一時的に隠して戻したときに元の進行へ戻せない、といったことがこの構造からは起こりうる。特定の実装の不具合ではなく、一つのフィールドで複数の性質を表すという形から出てくる性質である。

Axon が lifecycle という一つの状態へまとめているのは、採否と進行のように利用者が明示的に遷移させ、変更履歴を残したい段階だけである。導出できる値、機械が判定する条件、表示の都合は lifecycle に入れない。要素を分けてあると、要らない要素を持たない判断をしても他が壊れない。優先度と表示を持たない判断はこれで成立している。

## 導出値の定義を固定する理由

候補集合と一覧の状況の定義は、利用者が設定で変更できないものとする。

カスタマイズを許すと、検証の対象が一つのモデルではなく設定のパラメータ空間全体になり、全パラメータで不変条件が成り立つことを確かめるのは実質不可能になる。着手候補の定義に前提を失った Entity を含める設定が書けてしまえば、着手できないものが `axon tasks` に出る。

| カスタマイズの種類 | 可否 |
| --- | --- |
| 候補集合と状況の定義を変える | 禁止。不変条件が壊れる |
| 一覧の並び順、絞り込み、表示項目 | 自由。導出値を消費する側で、モデルの意味は変わらない |

原則として、カスタマイズしたくなったらモデルが間違っている兆候として扱う。設定で逃げるとモデルの誤りが隠れたまま運用される。個人用ツールなので、設定ではなくモデルを直す。

## 操作の反復を一律に扱わない理由

lifecycle 遷移は現在と異なる状態への遷移、関係と条件の設定は目標値の宣言、登録と Note は新しい実体や記録の生成である。性質が違うため、同じ操作を繰り返した結果も順に失敗、成功した no-op、新規追加となる。追加操作には idempotency key を導入せず、重複を避ける必要性が確認された時点で設計する。反復したときの結果は [CLIと表示の契約](../reference/cli.md#mutationの結果) に定める。

## メタ情報に専用フィールドを足さない理由

取りやめの理由、浮上したときに何を判断すればよいか、後送りの理由といったメタ情報に専用フィールドを設けず、本文・Note・状態変更履歴の理由で表す。lifecycle 遷移には任意の理由を添えられるため、取りやめの理由には専用フィールドが要らない。判断材料は description で足りる。理由の入力は必須にしない。理由を残せる経路があれば足りる。

フィールドを足すかどうかの基準は「無いとモデルが壊れるか」であり、これらは壊れない。

## Noteを追記専用にした理由

Note は編集・削除せず、訂正は新しい Note で行う。今の運用でこれに困っておらず、後から制限を厳しくするより緩めるほうが運用コストが低いためである。編集を許してから追記専用へ戻すと、既存の記録の意味を遡って決め直すことになる。

## Group を計画 Entity にした理由

Issue 間の dependency だけでは、計画に含まれる子タスクと、その計画全体が待つ外部の前提を区別できない。Group は Issue・Group を計画範囲として包含し、Group に置いた dependency と判断の frontier を配下へ効かせる独立した Entity とする。

Group は単なる分類ではない。利用者またはエージェントが計画単位を明示的に `Start` し、子孫を確認してから明示的に `Complete` する。子孫の集計は観測事実、Group の `Completed` は計画単位についての宣言であり、両者を同じ値にしない。

## 親 Group を一つに限る理由

Issue・Group は最大一つの親 Group を持つ。多重所属を許すと、複数の親が別々の lifecycle にあるときに配下の活性と判断範囲が矛盾する。包含を tree に保つことでこれを構造的に起こさない。共有する成果物は dependency、横断的な分類は一覧の絞り込みで扱う。

## ID を `<prefix>-<ランダム6文字>` にした理由

連番にはしない。識別子に意味を持たせないためである。`#12` と `#15` があると、エージェントも人間も「12 のほうが先に作られたから先にやるべき」「番号が若いほうが基盤的なタスクだろう」と推測する。優先度を持たないと決めているのに、ID が暗黙の優先度として機能してしまう。順序が要るなら順序として明示的に持つべきで、ID から漏れ出してはいけない。

乱数部分の桁数は 6、文字種は小文字の Crockford Base32 (`0-9a-z` から紛らわしい `i`・`l`・`o`・`u` を除く) とする。

| 桁数 | 空間 | 衝突確率 50% に達する件数 |
| --- | --- | --- |
| 4 | 約 105 万 | 約 1,300 件 |
| 6 | 約 10 億 | 約 41,000 件 |
| 8 | 約 1 兆 | 約 130 万件 |

誕生日問題を考えると、4 文字では個人の repository でも数千件で衝突のリスクが出る。6 文字なら実質的に気にしなくてよい。

prefix は意味を持ってよい。管理 root の名前なので「どの作業単位の Issue か」という実際に意味のある情報になる。意味を持たせないのは乱数部分だけである。

prefix に許す文字を ASCII 小文字の `a-z`、数字、ハイフンに限るのは、ID を shell で quote せずに扱えるようにするためである。空白や引用符が入りうる文字種を許すと、完全 ID を渡すたびに quote の判断が要り、エージェントが組み立てるコマンドで壊れやすくなる。空を許さず、先頭と末尾をハイフンにしないのも、ID を見て prefix と乱数部分の境界を迷わないためである。

省略時は管理 root の directory 名の ASCII 大文字を小文字化した結果を使い、規則に合わなければ保存先を作らずに失敗する。小文字化以外の自動補正をしないのは、利用者が意図していない prefix を黙って作らないためである。合わない場合は `axon init PREFIX` で明示する。

Issue と Group は同じ ID の namespace を使い、kind を ID に埋め込まない。CLI は一意であれば乱数部分だけでの参照も受け付ける。

## 重複着手を `axon start` の条件付き更新で防ぐ理由

複数のエージェント・セッションが同時に動くため、同じ Entity への `Start` の競合は日常的に起きる。しかも自動で動いているので人間が気づきにくく、二つのセッションが同じ Issue を実装して両方が成果を出してから発覚する、という壊れ方をする。

候補の確認と `axon start` は別の操作なので、同じ Entity への `axon start` が並行することはある。`axon start` は実行時点の Entity が着手可能であることを、現在値の更新と同じ保存境界で検査する。先に着手された Entity への更新は失敗するため、競合しても二重実装にはならない。競合後の扱いは呼び出し側の workflow が決める。

候補の選択と着手を一つの操作にまとめる入口は置かない。応答が欠落して再試行されると、そのたびに別の Entity へ着手する非決定的な副作用になり、一つのセッションが意図せず複数件を握るためである。候補一覧と、対象を明示した `axon start` に分けることで、再試行の対象を固定する。

予約状態や作業所有者を独立して持たない。「予約したが未着手」を作ると lifecycle との関係を別に定める必要があるが、実際には予約と着手はほぼ同時なので、`InProgress` と記録者情報で足りる。

## 記録者を既存の環境変数の規約から取る理由

エージェントの検出には規約が固まりつつある。独自の環境変数を要求するより既存の規約に乗るほうが、設定なしで動き、配布時の説明も要らない。取得の優先順位は明示指定、個別のエージェント検出、自己申告、実行ユーザーの順とする。個別検出を自己申告より先に見るのは、自己申告の値が冗長なことがあり、一覧で読みにくくなるためである。検出する具体的な環境変数と順位は [記録者連携](../development/lifecycle-recorder.md) に定める。

サポート対象は必要になってから足す。記録者は一覧と調査の手掛かりであり、操作の権限、排他制御、`axon release` の事前条件には使わない。`axon start` を実行した CLI 自身の process はコマンド終了と同時に終わるため、作業セッションの生存判定には使えない。エージェントの session ID にも Axon 内から照合・再開する経路はないため、保存はするが排他や表示の根拠にはしない。

放置された着手中の Entity を時間で自動解放しない。正常な作業が数日続くことがあり、経過時間の閾値に実用上の根拠がないためである。記録者を確認した人が `axon release` で明示的に解放する。Axon はエージェントのセッションログを検索・解釈しない。

## 外部コマンドを再浮上条件にした理由

リリースの公開や変更の取り込みといった外部の事実を、代理の Entity へ転記して終端させると、外部と Axon を同期する作業が増える。外部コマンドとして観測すれば、lifecycle や dependency の成果前提を代用せずに待てる。

日時で浮上してから判定し、未成立なら再度後送りする案は採らなかった。日時と観測結果の書き戻しを組み合わせると、条件の設定と外部観測が保存状態の上で混ざる。必要な導出で動的に評価し、同じ呼び出し内だけ結果を共有することで、重複実行を抑えつつ次回の変化を観測する。

判定の失敗を未成立へ丸めると、待ちが続いているのか条件のコマンドが壊れたのかを区別できない。失敗を一覧の失敗として返し、条件を修復する経路を残す判断にした。実行間隔・タイムアウト・永続キャッシュは外部コマンドへ委ね、Axon に scheduler や観測ログを持ち込まない。

日時まで待つ用途は残すが、日時・タイムゾーンの解釈や複合条件を Axon 側の条件型にはしない。専用条件に限定せず、設定する側が分かりやすい方法で判定できる柔軟さを優先する。

条件の種類として検討した `AfterEntity`（別 Entity の完了で浮上）も採らなかった。検討時に挙がった利用例では、主用途は成果の必須依存ではない監査対応の推奨順だった。候補から隠す必要はなく、推奨順の管理自体も必須ではないため、代替の順序機能も追加しない。実装・設計・運用の結果が必要な例は dependency で扱える。固有の用途が現れたら再検討する。

`Manual`（明示解除まで浮上しない）も採らなかった。設定後に忘れやすく、明示解除まで無期限に隠す用途を必要としないためである。日時まで待って見返し、必要なら日時を設定し直す運用を選ぶ。その日時待ちも外部コマンドで表現する。これらは専用の条件型を採用しない判断であり、外部コマンドの表現を制限するものではない。

条件の意味と評価の契約は [候補と外部条件](../reference/candidates.md) に定める。

## 操作案内と利用者の判断の境界

エラーには次の操作を含める。原因の事実だけを表示しても、利用者がデータを保持したまま再開する方法を特定できないためである。案内の有無ではなく、利用者の判断を代行するかどうかを境界にする。成立条件、確認先、選択肢とその効果は説明し、採否や計画変更の選択は利用者に残す。

## 実装言語に Rust を選んだ理由

要件は、状態遷移の規約を型で表現し、規約違反をコンパイル時に検出できることだった。

この要件で Go は落ちる。直和型がないため lifecycle や遷移のような限定された値の集合を型で表現できず、interface と型スイッチで代用しても網羅性の検査が効かない。状態や遷移を一つ足したときの対応漏れをコンパイラが検出できない。TypeScript は判別可能な union と `never` による網羅性検査で近いことはできるが、実行時の保証がなく、branded type も型注釈を外せば通る。

| 表現したいこと | 手段 |
| --- | --- |
| lifecycle と遷移が取りうる値の限定 | `enum` |
| 値を足したときの対応漏れの検出 | `match` の網羅性検査 |
| Entity の ID と素の文字列を取り違えない | newtype |
| 保存先から読んだ値が想定外なら落とす | 境界での `TryFrom` による検査 |

モデルの直和型がそのまま Rust の `enum` に対応するため、仕様と実装の距離が近い。最後の項目は「境界で検証し、内部は型を信頼する」方針にあたる。保存先から読んだ値を型へ変換する境界を一箇所へ集約し、別の読み出し経路に変換・検査を分散させない。

変更コストが高いことは承知の上で選んでいる。モデルを先に固めるため、後から変わるのは主に CLI の表層であり、そこは Rust でも変更コストが低い。

## 機能を持たずに始める判断

まず持たずに始めて、実際に困ってから足す。要素を性質で分けてあるため、持たない判断をしても他が壊れない。

後から足せるものを落として始めるときは、落とすための条件を先に決める。たとえば履歴を後回しにする条件は、状態更新の経路が一箇所に集約されていることだった。集約されていれば記録の追加を後から差し込めるが、更新経路が散らばっていれば記録漏れを探して回ることになる。

判断を保留したものは `Undecided` の Issue として登録する。`Undecided` は `axon tasks` に出ないため、作業候補を汚さない。

コマンド名や出力は紙の上で詰めず、実装しながら決める。実際に打つと必ず変わるうえ、間違えても保存した情報の作り直しが要らないためである。

## 一括 declaration の設計判断

契約は [Declaration](../reference/declaration.md) にある。ここには、その設計時に検討した目的・保存境界、個人 workflow の判断境界、採らなかった案を残す。

### 目的と保存境界

一括編集の目的は、新しく大きめの計画を一括で登録することと、登録後の計画全体を context に入れて役割・完了条件・依存の不整合を見つけ、レビュー可能な artifact として扱い、修正をまとめて反映することである。設計では以下を検討し、契約へ反映した。

- 取得する計画境界、包含、外部参照を明確にし、一覧の非表示を削除指示と取り違えない。
- 完全な宣言と部分変更を区別する。省略が維持・解除・削除のどれかを曖昧にしない。
- 変更前後の計画全体と差分を、保存前に確認できるようにする。
- 取得後に前提が変わった場合は競合として扱い、意図を再照合する。ID や digest の再生成で競合を隠さない。
- 全体の包含・dependency・終了構成を検査し、部分的な適用で不整合を残さない。
- 新規 ID を固定して再実行時の重複作成を防ぐ。コマンド名や file 形式は目的と安全性を確定してから決めた。
- 保存先への適用と declaration artifact への書戻しを別の保存境界として扱い、部分適用・結果不明を区別する。
- 入力・backup・途中の artifact を保全し、未適用が立証できる操作だけを安全に再試行する。

利用者から artifact を受け取る場合は、その形式、内容、要求された変換と必要な保存結果を把握する。機能が非対応であれば、その事実と入力を呼び出し側へ返し、無断の逐次 CLI 操作や保存 file の直接編集で代用しない。

### 個人 workflow の判断境界

依頼が指定する計画範囲、declaration file への反映、保存先への反映を区別する。file の作成・レビューだけの依頼から、保存済み Entity の変更へ広げない。明示された適用の直前で同じ権限を再確認しない。

利用者が所有する file は内容と出典を調べてから扱い、都合のよい `axon export` で上書きしない。呼び出し側が固定した snapshot・候補・digest を保全し、取得後の編集を artifact の再生成で消さない。エージェントが所有する作業 file でも、結果不明の照合に必要な間は保持する。

合意済みの目的・範囲・完了条件から一意に決まる構成の整理は自律できる。新しい目的、採否、独立した完了単位、代替前提の選択は利用者の判断に返す。一括編集という形式は、それらの判断権限を与えない。

本文編集・lifecycle・構造の責務を守る。複数段階になる場合は前段の適用結果を保持し、後段が失敗した後の状態を説明する。自動 rollback や補償の判断を発明しない。

競合では新しい保存情報と元の意図を比較し、同じ効果へ解決できる訂正だけを進める。意味上の選択が変わる場合は具体的な差と案を返す。必要な入力や判断が揃うまでは artifact を保持し、未対応の機能を実行可能と報告しない。

### 採らなかった案

- 全体取得と一括適用を別の契約に分ける案。`axon export` は適用の前提でもあり、同じ形式を二度定義することになるため、一つの契約にする。
- `prepare` を `apply` または `check` に吸収する案。`apply` に吸収すると結果不明時に新規 ID が分からず、`check` に吸収すると検証のつもりで file が書き換わる。
- Note を declaration に読み取り専用で同梱する案、および配下の全 Note をまとめて読む入口を同時に作る案。同梱すると Note の追加による競合、file 内の Note の書き換え、適用後の書戻しの扱いを決める必要が増える。この機能の用途は計画の登録と修正であり、Note は含めない。
- 再浮上条件を編集対象または読み取り専用として載せる案。考慮事項を増やさないため扱わず、適用は現在の条件を保持する。
- JSON または独自の Markdown 形式。JSON は複数段落の description の改行を潰し、独自形式は parser と canonical 化を自作することになる。
- Group の下に子を入れ子で書く形式。親を入れ子と `parent` の二通りで表せて canonical 形が一意でなくなり、選択範囲の外に親を持つ Entity の扱いも複雑になる。
- 素の文字列による参照。`key` の文字種は ID の形と重なり得るため、見分けの規則を増やすより明示する。
- 元の値へ戻った変更を競合として検出する案。値が同じなら編集の意図はそのまま適用できる。
- declaration による lifecycle 遷移。`Accept`・`Start`・`Complete` の前提検査を declaration 用に二重化することになり、計画の workflow が着手・完了へ権限を広げない境界とも一致しない。
- 保存先全体を一括で取得する selector。最上位の Entity をすべて渡せば同じ結果が得られ、`Completed` が積み上がると artifact として扱いにくい。
- 全 Note と全直接関係を canonical JSON として `base` に埋め込み、取得時の観測から前提の一致と結果の一致を独立に判定する方式。Note の本文が YAML 側と `base` 側に二重に入り、計画を context として読み編集する artifact が大きくなる。
- Note・条件・外部から入る関係を同梱し、編集集合や外部参照への Note の追記も競合として止める方式。エージェントが Note を頻繁に追加する運用では、計画の編集意図と無関係な変化による停止が増え、復旧に手作業の移し替えを要する。外部参照は存在と共通コアの制約だけを検査する。
- 共通コアに一括編集専用の候補構築と差分 guard を置く方式。適用は通常操作の列であり、専用の guard は通常操作の guard を二重化する。適用順序と guard を突き合わせた範囲では、有効な最終状態を誤って拒否する経路は見つかっておらず、専用の検査経路を増やす根拠がなかった。この突き合わせは全経路の証明ではない。
- declaration に保存先の識別子を持たせる方式。既存 record の ID が適用先に存在しなければ拒否するため、新規 Entity だけで外部参照を持たない declaration は保存先をまたいで使える。artifact を一つの保存先へ結び付ける制約は加えない。これは、同じ ID を持つ保存先どうしを識別する保証ではない。
- Group の直下だけを選ぶ selector。計画全体を context として読む目的に合わせ、Group は常に全子孫を選ぶ。取得の境界を直下と再帰で切り替える操作は増やさない。
- JSON path 形式の診断。YAML 入力に対する診断は行・列と抜粋で位置を示す。
