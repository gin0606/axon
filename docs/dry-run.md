# 運用シナリオのドライラン

`axes.md` で固めた状態モデルを、実際の作業に通して穴を探す。
モデル検査は内部の無矛盾性しか見ていないため、運用で必要な操作が足りるかは別に確かめる。

## シナリオ 1: self-review の指摘を投げ込む

PR のレビューで 5 件の指摘が出た状況。分類と表現:

| 指摘の性質 | モデルでの表現 | 判定 |
| --- | --- | --- |
| 今のスコープで直す (2 件) | issue にせずその場で直す | 問題なし |
| 本当はやるべきだがスコープ外 (1 件) | A=未着手 / B=採用 / C=? | **問題あり (下記 1-a)** |
| 真っ当そうだが今判断するコストを避けたい (1 件) | A=未着手 / B=未判断 / C=1 ヶ月後 | 問題なし。当初の動機がここで解決している |
| 対応不要と判断 (1 件) | B=不採用 で記録、または issue を作らない | 問題なし |

### 問題 1-a (決着): 「今のスコープが終わったら着手」を表現しにくい

→ **C-1 を差し替えて解決**。C の条件に「他 issue / グループが終端に達すること」を許す。
　欲しかったのは soft 順序 (ready に残す) ではなく ready から外すことなので、C の守備範囲だった。
　以下は発見時の記録。


「やると決めたが、今の作業が片付いてから」を書きたい。手段は 3 つあるがどれも噛み合わない。

- `C = 適当な日付 (1 週間後)` — 実際の条件は日付ではないので、早すぎ/遅すぎが起きる
- `D = 現在の作業 issue に依存` — D は前提依存 (成果物が要る) の意味。ここでは成果物は要らない
- `C = null` で ready に出す — 今のスコープの作業と混ざる。**投げ込むと ready が汚れる**という元の不満の再現

G-4 で soft 順序を落とした影響がここに出ている。ただし実用上は日付で妥協できる範囲かもしれない。

## シナリオ 2: 大きな epic を駆動する

9 つの機能群グループ、共通基盤グループ、96 issue を計画して回す状況。

| 操作 | モデルでの表現 | 判定 |
| --- | --- | --- |
| グループと子グループを作る | G-5 (階層無制限) | 問題なし |
| 共通基盤に他グループを依存させる | グループ間 hard 依存 | 問題なし |
| 次に何をやるか見る | ready | 問題なし |
| 進捗を見る | 分母 = B=採用 の子孫 | 問題なし |
| 96 件の issue を計画時に作る | **B の初期値は?** | **問題あり (下記 2-a)** |

### 問題 2-a (取り下げ): issue 作成時の B (採否) の初期値が決まっていない

→ **問題ではなかった**。作成時に明示的に指定すればよい。
　br の失敗は「デフォルト値があること」ではなく「未判断を表す値がなかったこと」で、
　それは B-1 派生で決着済み。作成経路を分けるのは CLI の入口設計の話でモデルの問題ではない。
　以下は発見時の記録。


計画から作る issue は「やると決めたもの」なので B=採用。
一方、投げ込む issue は「まだ判断していない」ので B=未判断。
**同じ作成操作で初期値が違う**が、どちらをデフォルトにするかを決めていない。

- 初期値=未判断 にすると、計画で作った 96 件を後から全部採用に変える手間が出る
- 初期値=採用 にすると、投げ込みが自動的に「やると決めた」になる。
　これは br の priority のデフォルトが medium で「未検討」を表現できなかったのと同じ構図

作成経路 (計画から作る / 投げ込む) で初期値を変える案があるが、
「経路によって状態が変わる」のは暗黙の挙動になりやすい。

## シナリオ 3: worktree での並行作業・セッション間の引き継ぎ

状態の同期・永続化の問題であり、状態モデルの問題ではない。
データモデルと永続化の設計で扱う。ここでは判定しない。

## シナリオ 4: br からの移行

| br の status | 新モデル | 判定 |
| --- | --- | --- |
| open | A=未着手 / B=採用 | br は採否を持たないので、暗黙に採用として移す |
| in_progress | A=着手中 / B=採用 | 問題なし |
| blocked | 状態としては持たない (依存から導出) | 問題なし |
| deferred | A=未着手 / B=採用 / C=defer_until | 問題なし |
| draft | A=未着手 / B=未判断 | 妥当な対応付け |
| closed | A=終了 / B=? | **問題あり (下記 4-a)** |
| tombstone | 削除 | 問題なし |
| pinned | 捨てる (G で表示は持たない) | 情報は失われるが意図どおり |

### 問題 4-a: `closed` に「完了した」と「やらないことにした」が畳まれている

移行時に A=終了 までは決まるが、B が採用か不採用か判別できない。
close_reason のテキストから推測するしかない。
→ 一律 B=採用 で移し、必要なら後から個別に直す、が現実的。

### 問題 4-b: soft 順序として使っていた `related` が失われる

実運用では「先にやったほうが効率が良い」を `related` で表現していた。
G-4 で soft を落としたため、移行先がない。description に落とすか、捨てる。

## 見つかった問題のまとめ

| | 内容 | 重さ |
| --- | --- | --- |
| 2-a | issue 作成時の B の初期値が未決 | **取り下げ** — 作成時に明示指定すればよい |
| 1-a | 「今のスコープが終わったら」を表現しにくい | **決着** — C-1 を差し替え (C の条件に参照を許す) |
| 4-a | 移行時に closed の採否が判別できない | 小 — 移行時の一度きり |
| 4-b | 移行時に related が失われる | 小 — G-4 の決着の帰結 |
