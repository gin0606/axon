# CLI

## 方針

- **出力は簡潔なテキスト 1 本**。JSON は作らない。主要な利用者がコーディングエージェントであり、JSON はキー名が繰り返されるぶんトークンを食う。自然言語のほうが読みやすく短い。スクリプトから使う必要が出てから足す
- **コマンド名に意図を持たせる**。汎用的な動詞 (`add` 等) を避ける。迷ったエージェントが「デフォルトらしいもの」に吸い寄せられるのを防ぎ、意図の表明を強制する
- **`--help` がモデルの説明になる**ように、軸ごとの操作をサブコマンドにまとめる

この文書は開発者が CLI の操作意味と設計理由を日本語で読むための正であり、help には埋め込まない。利用者向けの英語 help は `docs/help.md` に分離し、操作契約を自己完結して説明する。両者は完全な対訳ではなく、設計変更時は開発者向けの理由と利用者向けの契約をそれぞれ更新する。Usage、引数、option、コマンドツリーは Clap の定義から生成する。短いコマンド一覧だけが必要なら `axon -h`、完全な利用マニュアルは `axon --help` または `axon help all`、個別の Usage は `axon help <command path>` または `axon <command path> --help` を使う。

今回この文書を日本語のまま維持するのは、現在の開発者の読解コストを増やさないためであり、プロジェクトの恒久的な言語方針ではない。開発者・利用者層が変わった場合は、文書全体の英語化を改めて判断する。

## 操作契約

### 状態の軸と導出値

issue は独立した 3 軸と 2 種類の関係を持つ。

| 分類 | 値と意味 |
| --- | --- |
| A 進行 | 未着手 / 着手中 / 終了。「終了」は、やり切ったかどうかではなく、もう進めないことを表す |
| B 採否 | 未判断 / 採用 / 不採用。やると決めたかを表す |
| C 時期 | 日付または他 issue の終了を条件に、いつ再び意識に上げるかを表す。条件なしなら常に浮上する |
| issue 依存 | 相手の成果物がないと始められないという前提 |
| グループ | issue を機能群にまとめる階層。グループ間にも依存を張れる |

`ready` / `blocked` / `orphaned` / `surfaced` / `terminal` / blocking cause / グループ進捗は保存せず、上の状態と関係から読み取り時に導出する。

- **ready** — 未着手・採用・浮上中で、未解決の issue 依存もグループ依存もなく、前提喪失でもない
- **blocked** — 未終端の依存先がある
- **orphaned (前提喪失)** — 依存先が不採用になり、必要な成果物を得られない。依存元の採否は自動変更せず、人間の判断を待つ
- **blocking cause** — 依存を遡って、前提喪失、後送り中、または未解決の葉にある root cause を示す

進行と採否は別々に読む。`終了 × 採用` はやり切った状態、`終了 × 不採用` は着手後に打ち切った状態、`終了 × 未判断` は調査を終えて採否を待つ状態になる。1 つのコマンドで複数の軸を暗黙に変えない。

### 候補を探す 3 つの経路

| コマンド | 答える問い | 主な対象 |
| --- | --- | --- |
| `axon ready` | 今、機械的に着手可能なのはどれか | ready な issue |
| `axon triage` | 人間の判断が必要なのはどれか | 未判断、前提喪失 |
| `axon list` | 登録されているものを状態に関係なく全て見たい | 依存待ち、後回し中、着手中、終了済み、不採用を含む全 issue |

`plan` は作成と同時に採用し、`capture` は未判断で作成する。したがって `capture` した issue は `ready` ではなく `triage` に現れる。`ready` と `triage` のどちらにも出ないものを探すときだけ `list` を使う。

### 標準フロー

1. リポジトリごとに一度 `axon init` を実行する。
2. やると決めた作業は `axon plan <title>`、判断前の懸念は `axon capture <title>` で登録する。
3. `axon ready` から対象を選び、`axon start <id>` でその 1 件への着手を記録する。`start` は候補を自動選択せず、同じ issue の二重着手を拒否する。
4. 必要なら `axon write <id>` で説明や申し送りを残し、作業が終わったら `axon done <id>` で終了する。
5. `axon triage` に出たものは `show` と `log` で材料を確認し、`decide accept` / `decide reject` で採否を決める。前提喪失なら、依存を外して続けるか、依存元も不採用にするかを判断する。

作業セッションが落ちて着手だけが残った可能性があるときは `stale` で検出し、既存の着手者を確認してから `release` する。`stale` は自動解放しない。

### 読み取りと状態変更

読み取りだけを行うのは `ready`、`triage`、`list`、`show`、`log`、`stale`、`group list`、`group show`、`completion` と help/version である。それ以外は DB の初期化、issue やグループの作成、またはいずれかの軸・関係・文面を変更する。

候補の読み取りと変更は分けてある。`ready` は着手せず、`triage` は採否を変えず、`stale` は claim を解放しない。変更コマンドには対象 ID または slug を明示する。

変更操作の反復時の扱いは、その意味から決める。`start` / `done` / `release` / `decide` / `when` は状態遷移なので、事前条件違反や同値指定では失敗する。`write` / `group set` / `group unset` / `dep add` / `dep rm` / `group dep add` / `group dep rm` / `group reject` は目標値や集合の設定なので、目標をすでに満たしていれば成功 no-op になる。`plan` / `capture` は追加操作なので、呼び出すたびに新しい issue を作る。

失敗した状態遷移は、状態、履歴、`updated_at` を変えない。設定の成功 no-op も `updated_at` を変えず、`group reject` はすでに不採用の issue に判断履歴を追加しない。

### 出力と終了コード

- help、補完スクリプト、検索結果、詳細、状態変更の確認は **stdout** に出す。help と `completion` は DB を開かず、成功時は終了コード 0 になる
- 引数や操作のエラーは **stderr** に出し、非 0 で終了する
- `ready` / `triage` / `list` に行がない場合は、パイプに案内文を混ぜないため stdout を空にし、案内だけを stderr に出して終了コード 0 にする
- issue を行単位で返す一覧 (`ready` / `triage` / `list`) は、空白区切りの第 1 列を常に ID にする。`axon ready | fzf --preview 'axon show {1}'` のように扱える

### 保存場所、worktree、ID

データは git 管理外の SQLite DB `.axon/axon.db` に保存する。git worktree では `git rev-parse --git-common-dir` から共通のリポジトリ位置を求めるため、同じリポジトリの全 worktree が 1 つの DB を共有する。

issue ID は `<prefix>-<ランダム 6 文字>` の形式で、prefix は `axon init` の引数、またはリポジトリのディレクトリ名から決まる。コマンドには完全な ID のほか、`a3f9k2` のような prefix を除いた 6 文字も渡せる。短縮形が複数件に一致する場合は候補を示して失敗する。グループは人が付けた slug で参照する。

## 機能ごとの目的

コマンドの一覧と各コマンドの一行説明は `axon --help` にある。ここには目的と設計判断を書く。

**目的の欄に「〜を見る」のような動作しか書けないなら、そこは詰められていない。**新しい機能を足すときも、この欄を埋められるかで判断する。

### init

**目的**: リポジトリで axon を使い始める。issue ID の接頭辞を決める。

**設計**: 接頭辞は既定でリポジトリのディレクトリ名。ID を `<接頭辞>-<ランダム 6 文字>` にするのは、番号から順序を推測させないため (`data-model.md` D-2)。

### completion

**目的**: シェル上でサブコマンド、オプション、静的に定まる値を発見しながら入力できるようにする。

**設計**: `completion <shell>` は Clap のコマンド定義から Bash / Elvish / Fish / PowerShell / Zsh 用の補完スクリプトを標準出力へ生成する。CLI と補完の定義を二重管理せず、DB 由来の issue ID や group slug は動的補完しない。

### plan / capture

**目的**: 作成時に採否を表明させる。

**設計**: `add` のような汎用的な動詞をデフォルトに置くと、迷ったエージェントがそこに吸い寄せられ、投げ込んだものが自動的に「やると決めた」ことになる。B の軸を分けた意味が消える。どちらの名前も意図を持つため、選択を強制できる。

### ready / start

**目的**: 着手可能な issue を見つけ、指定した issue への着手を記録する。

**設計**: `ready` は候補を読み取るだけにし、`start <id>` は指定された issue だけを claim する。候補の選択と状態更新を分ける。

`start` は実行時点で issue が ready であることを、claim の更新と同じトランザクションで検査する。同じ issue への実行が並行しても 1 つだけ成功し、二重着手を防げる。

成功した `start` は actor と時刻を状態遷移と同じトランザクションで進行履歴に残す。理由の入力は求めない。

候補を自動選択して着手するコマンドは置かない。応答の欠落などで同じコマンドが再実行されると、呼ぶたびに別の issue を claim してしまい、操作を再試行安全にできないため。

### done

**目的**: 作業を終え、次に着手可能になったものをその場で知る。

**設計**: 依存が解けて何ができるようになったかを出すことで、改めて `ready` を叩かなくてよい。`-r` の内容は作業結果として、終了への状態遷移と同じトランザクションで進行履歴に残す。

認める遷移は `着手中 → 終了` だけ。未着手または終了済みの issue への実行は非 0 で終了し、進行履歴を追加しない。更新時の条件として検査するため、同時実行でも 1 つの遷移だけが成功する。

### triage

**目的**: 人間の判断を待っているものを知る。やることが尽きたときや時間が空いたときに、ここを見て採用/不採用に振り分ける。

**設計**: 対象は 2 種類。どちらも機械には決められない。

- **未判断** — やるかどうかを決めていない
- **前提喪失** — 依存先が不採用になった。依存を切って続けるか、こちらも不採用にするか

`ready` が「機械が着手できると判定したもの」を返すのに対し、`triage` は「機械が人間の判断が要ると判定したもの」を返す。対になっている。

前提喪失を一覧するのはここだけ。`orphaned` を推移させない設計は「根本にあるものを人が定期的に見る」ことを前提にしているため、その経路が要る (`axes.md` D-1 派生)。

### list

**目的**: axon に入れたものが必ず取り出せることを保証する。

**設計**: `ready` にも `triage` にも出ないもの (依存待ち・後回し中・着手中・終了済み・不採用) を拾う唯一の経路。日常的に使うものではなく、取りこぼしを防ぐためにある。状態と、なぜ ready に出ないのか (待ち / 前提喪失 / 浮上日) を併記する。

### show

**目的**: issue が何を待ち、何を待たせ、どの群に属すかと、これまでの進行を 1 画面で知る。止まっているならその原因も知る。

**設計**: 直接の待ち相手だけでなく、その奥にある原因 (前提喪失・後送り中) やグループ依存まで遡る。`orphaned` を推移させない設計のため、これが無いと依存の鎖の先で不採用が出たときに「ただの待ち」と区別がつかない (`axes.md` D-1 派生)。

依存は両向きに出す。依存先 (待ち / 済み / 前提喪失) に加えて、依存元を「後続」として並べ、これを終わらせると何が動くかを同じ画面で読めるようにする。すでに終端の後続は動かないのでその旨を添える。該当が無い区分は行ごと出さない。

`start` / `done` / `release` は進行履歴としてここに表示する。これは A 軸の状態遷移に結び付いた記録であり、B/C の判断を表示する `log` とは分ける。

状態、依存、グループ、進行履歴は 1 つの読み取りトランザクションから取得する。並行する状態変更の前後を混ぜず、`show` の 1 回の出力を同じ時点のスナップショットとして扱う。

### log

**目的**: 「なぜやるのか」「なぜやらないのか」「なぜ今やらないのか」を後から辿る。類似の問題を考えるときや、決定を再考するときに参照する。

**設計**: 対象は採否 (`decide`) と時期 (`when`) の変更だけ。進行や文面の編集は含まない。着手・終了・編集を並べると、理由のある判断がその中に埋もれるため。進行は失わず、`show` の進行履歴に分けて表示する。

### write

**目的**: issue の文面 (表題と説明) を直す。理解が変わって表題が実態とずれたときと、タイトル一行に入らない情報を残すときの両方を扱う。作業を中断するときの申し送りもここに書く。

**設計**: 表題と説明はどちらも「この issue が何か」の記述なので、1 コマンドで扱う。書き換えの対象がこの 2 つより増えることはないため、`edit` のような対象を選ばない名前は避けた。

説明の入力は `-m` と `-F` (`-` で標準入力) だけ。`$EDITOR` を開く経路は置かない。端末が要るため主要な利用者には使えず、フラグなしの起動をそこに落とすと、方針の「デフォルトらしいもの」そのものになる。フラグを 1 つも渡さない起動はエラーにする。

`--title` だけを渡したときは説明に触らない。

### stale / release

**目的**: セッションが落ちて着手中のまま残ったものを見つけ、解放する。

**設計**: 一定時間動きがなく、かつ着手したプロセスが終了しているものに限る。時間だけで判断すると長時間の作業を誤検出する。検出しても自動では解放しない。生きているセッションの claim を奪う危険があるため (`data-model.md` D-6)。`release -r` の内容は解放理由・申し送りとして、未着手へ戻す状態遷移と同じトランザクションで進行履歴に残す。

認める遷移は `着手中 → 未着手` だけ。それ以外の状態への実行や同時実行で先を越された操作は非 0 で終了し、進行履歴を追加しない。

### decide

**目的**: やるかどうかを決める (軸 B)。

**設計**: 判断として記録される。`-r` で理由を残す。

### when

**目的**: いつ再び意識に上げるかを決める (軸 C)。

**設計**: `dep` と意味が違う。参照先が不採用になったとき、`when after` は待つ理由が消えて浮上し、`dep` は前提喪失になる (`axes.md` C-1)。判断として記録される。

### dep

**目的**: これが無いと始められない、という前提を表す (軸 D)。

**設計**: 前提の 1 種類のみ。順序の希望は依存を張らずに済ませる。型を増やしても意味論を定義しなければ注釈が増えるだけで、判断は自動化されない (`axes.md` D-1 派生)。

### group

**目的**: 機能群でまとめ、群の単位で依存を張る。基盤が終われば依存する機能群を並列に着手できる。

**設計**: グループは状態を持たない容れ物で、進捗も完了も子から導出する。グループ間依存は全子孫が終端に達したら解除し、不採用が混じっていても解除する。祖先グループの依存は子グループにも効く (`axes.md` §6)。
