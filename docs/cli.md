# CLI

## 方針

- **出力は簡潔なテキスト 1 本**。JSON は作らない。
　主要な利用者がコーディングエージェントであり、JSON はキー名が繰り返されるぶんトークンを食う。
　自然言語のほうが読みやすく短い。スクリプトから使う必要が出てから足す
- **コマンド名に意図を持たせる**。汎用的な動詞 (`add` 等) を避ける。
　迷ったエージェントが「デフォルトらしいもの」に吸い寄せられるのを防ぎ、意図の表明を強制する
- **`--help` がモデルの説明になる**ように、軸ごとの操作をサブコマンドにまとめる

## 命名

コマンドの一覧と各コマンドの説明は `axon --help` にある。ここには意図だけ書く。

- **`plan` と `capture` を分けている** — 作成時に採否を必ず表明させるため。
　`add` のような汎用的な動詞をデフォルトに置くと、迷ったエージェントがそこに吸い寄せられ、
　投げ込んだものが自動的に「やると決めた」ことになる。B の軸を分けた意味が消える
- **軸ごとの操作をサブコマンドにまとめている** (`decide` / `when` / `dep` / `group`) —
　`--help` がそのままモデルの説明になり、エージェントが軸の構造を理解した状態で操作できる
- **`when after` と `dep add` は意味が違う** (`axes.md` C-1)。
　参照先が不採用になったとき、`when after` は条件が満たされて浮上し、`dep` は前提喪失になる
- **`describe` はエディタに本文だけを出す。** 説明用のヘッダを混ぜると
　Markdown の見出しと区別できなくなるため。本文が長くなるので、記録には先頭だけ残す

## 何が出力されるか

`--help` に書けない、出力の意図。

- **`done` は終了後に着手可能になったものを挙げる。** 依存が解けて次に何ができるようになったかを、
　エージェントがその場で知るため。改めて `ready` を叩かなくてよい
- **`show` は止まっている理由を遡って表示する。** 直接の待ち相手だけでなく、
　その奥にある原因 (前提喪失・後送り中) やグループ依存まで辿る。
　`orphaned` を推移させない設計のため、これが無いと依存の鎖の先で不採用が出たときに
　「ただの待ち」と区別がつかない (`axes.md` D-1 派生)
- **`log` は判断の記録を出す。** 採否 (`decide`) と時期 (`when`) の変更だけが対象で、
　進行や本文の編集は含まない。`-r/--reason` で残した理由が並ぶので、
　「なぜやるのか」「なぜやらないのか」「なぜ今やらないのか」を後から辿れる
- **`stale` は放置された着手だけを挙げる。** 一定時間動きがなく、かつ着手したプロセスが
　終了しているものに限る。時間だけで判断すると長時間の作業を誤検出するため。
　検出しても自動では解放せず `release` を案内する。
　生きているセッションの claim を奪う危険があるため (`data-model.md` D-6)

## ready / start / next の住み分け

想定する運用が 2 通りあるため、3 つとも必要になる。

| 運用 | 使うコマンド |
| --- | --- |
| 人間が `ready` を見て、複数のエージェントに割り振る | `ready` で閲覧 → 各エージェントが `start <id>` |
| エージェントが自律的に次を取る | `next` |

`next` は取得と着手が 1 トランザクションなので競合しない。
`start` は人間が割り振りを誤ったときのために、既に claim されていたら失敗する。
