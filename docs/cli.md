# CLI

## 方針

- **出力は簡潔なテキスト 1 本**。JSON は作らない。
　主要な利用者がコーディングエージェントであり、JSON はキー名が繰り返されるぶんトークンを食う。
　自然言語のほうが読みやすく短い。スクリプトから使う必要が出てから足す
- **コマンド名に意図を持たせる**。汎用的な動詞 (`add` 等) を避ける。
　迷ったエージェントが「デフォルトらしいもの」に吸い寄せられるのを防ぎ、意図の表明を強制する
- **`--help` がモデルの説明になる**ように、軸ごとの操作をサブコマンドにまとめる

## 機能ごとの目的

コマンドの一覧と各コマンドの一行説明は `axon --help` にある。ここには目的と設計判断を書く。

**目的の欄に「〜を見る」のような動作しか書けないなら、そこは詰められていない。**
新しい機能を足すときも、この欄を埋められるかで判断する。

### init

**目的**: リポジトリで axon を使い始める。issue ID の接頭辞を決める。

**設計**: 接頭辞は既定でリポジトリのディレクトリ名。ID を `<接頭辞>-<ランダム 6 文字>` に
するのは、番号から順序を推測させないため (`data-model.md` D-2)。

### plan / capture

**目的**: 作成時に採否を表明させる。

**設計**: `add` のような汎用的な動詞をデフォルトに置くと、迷ったエージェントがそこに吸い寄せられ、
投げ込んだものが自動的に「やると決めた」ことになる。B の軸を分けた意味が消える。
どちらの名前も意図を持つため、選択を強制できる。

### ready / next / start

**目的**: 次に何をやるかを決める。

**設計**: 想定する運用が 2 通りあるため 3 つとも要る。

| 運用 | 使うコマンド |
| --- | --- |
| 人間が見て複数のエージェントに割り振る | `ready` で閲覧 → 各エージェントが `start <id>` |
| エージェントが自律的に次を取る | `next` |

`next` は取得と着手が 1 トランザクションなので競合しない。
`start` は人間が割り振りを誤ったときのために、既に claim されていたら失敗する。

### done

**目的**: 作業を終え、次に着手可能になったものをその場で知る。

**設計**: 依存が解けて何ができるようになったかを出すことで、改めて `ready` を叩かなくてよい。

### triage

**目的**: 人間の判断を待っているものを知る。やることが尽きたときや時間が空いたときに、
ここを見て採用/不採用に振り分ける。

**設計**: 対象は 2 種類。どちらも機械には決められない。

- **未判断** — やるかどうかを決めていない
- **前提喪失** — 依存先が不採用になった。依存を切って続けるか、こちらも不採用にするか

`ready` が「機械が着手できると判定したもの」を返すのに対し、
`triage` は「機械が人間の判断が要ると判定したもの」を返す。対になっている。

前提喪失を一覧するのはここだけ。`orphaned` を推移させない設計は
「根本にあるものを人が定期的に見る」ことを前提にしているため、その経路が要る
(`axes.md` D-1 派生)。

### list

**目的**: axon に入れたものが必ず取り出せることを保証する。

**設計**: `ready` にも `triage` にも出ないもの (依存待ち・後回し中・着手中・終了済み・不採用) を
拾う唯一の経路。日常的に使うものではなく、取りこぼしを防ぐためにある。
状態と、なぜ ready に出ないのか (待ち / 前提喪失 / 浮上日) を併記する。

### show

**目的**: issue の状態を知り、止まっているならその原因を知る。

**設計**: 直接の待ち相手だけでなく、その奥にある原因 (前提喪失・後送り中) や
グループ依存まで遡る。`orphaned` を推移させない設計のため、これが無いと依存の鎖の先で
不採用が出たときに「ただの待ち」と区別がつかない (`axes.md` D-1 派生)。

### log

**目的**: 「なぜやるのか」「なぜやらないのか」「なぜ今やらないのか」を後から辿る。
類似の問題を考えるときや、決定を再考するときに参照する。

**設計**: 対象は採否 (`decide`) と時期 (`when`) の変更だけ。進行や本文の編集は含まない。
着手・終了・編集を並べると、理由のある判断がその中に埋もれるため。

### describe

**目的**: タイトル一行に入らない情報を残す。作業を中断するときの申し送りもここに書く。

**設計**: エディタには本文だけを出す。説明用のヘッダを混ぜると Markdown の見出しと
区別できなくなるため。本文が長くなるので、判断の記録には先頭だけ残す。

### stale / release

**目的**: セッションが落ちて着手中のまま残ったものを見つけ、解放する。

**設計**: 一定時間動きがなく、かつ着手したプロセスが終了しているものに限る。
時間だけで判断すると長時間の作業を誤検出する。
検出しても自動では解放しない。生きているセッションの claim を奪う危険があるため
(`data-model.md` D-6)。

### decide

**目的**: やるかどうかを決める (軸 B)。

**設計**: 判断として記録される。`-r` で理由を残す。

### when

**目的**: いつ再び意識に上げるかを決める (軸 C)。

**設計**: `dep` と意味が違う。参照先が不採用になったとき、`when after` は待つ理由が消えて
浮上し、`dep` は前提喪失になる (`axes.md` C-1)。判断として記録される。

### dep

**目的**: これが無いと始められない、という前提を表す (軸 D)。

**設計**: 前提の 1 種類のみ。順序の希望は依存を張らずに済ませる。
型を増やしても意味論を定義しなければ注釈が増えるだけで、判断は自動化されない
(`axes.md` D-1 派生)。

### group

**目的**: 機能群でまとめ、群の単位で依存を張る。基盤が終われば依存する機能群を並列に着手できる。

**設計**: グループは状態を持たない容れ物で、進捗も完了も子から導出する。
グループ間依存は全子孫が終端に達したら解除し、不採用が混じっていても解除する。
祖先グループの依存は子グループにも効く (`axes.md` §6)。
