# 状態と用語

CLIに出る状態名と、操作を使い分けるための基本概念をまとめます。

## 三つの軸

| 軸 | 答える問い | 値 |
| --- | --- | --- |
| 進行（Progress） | 作業はどこまで進んだか、これ以上進めるか | `NotStarted`（未着手）・`InProgress`（着手中）・`Ended`（終了） |
| 採否（Disposition） | この仕事や結果を採用するか | `Undecided`（未判断）・`Accepted`（採用）・`Rejected`（不採用） |
| 再浮上条件（Resurface condition） | いつまた意識に上げるか | `Always`（常時）・`AtDate`（時刻）・`AfterEntity`（別のEntityの決着）・`Manual`（明示解除まで待機）・`Command`（コマンド） |

例えば「採用したけれど来月また考えたい」なら、採用のまま再浮上条件に時刻を設定します。作業中のIssueでも同様です。後回しにするために進行状態を未着手へ戻す必要はありません。条件を満たしても、採用や着手が自動で行われることはありません。

「終了」は、それ以上作業を進めないという意味です。採用した仕事の完遂のほか、不採用として打ち切った仕事、調査が終わって結果の採否を待つ仕事も、軸の組み合わせで区別します。終了した作業を再開する操作はなく、追加の仕事は別のIssueにします。

## 再浮上は、もう一度見るための条件

時刻は締切や着手予約ではありません。「その時刻になったらまた見る」という意味です。判断できる時期が分からなければ、明示的に解除するまで見送ることもできます。

コマンド条件は、外部ITSの状態やライブラリのリリースなどを、利用者が用意したスクリプトで判定します。条件は`ready`などの操作で必要になったときに評価します。バックグラウンドで監視・通知する機能ではありません。具体例は[ライブラリのリリースを待つ](usage.md#ライブラリのリリースを待つ)を参照してください。

## 成果が必要なのか、決着を待ちたいのか

| 関係 | 使いたい場面 | 相手が不採用になったら |
| --- | --- | --- |
| 依存（dependency） | Aの成果がないとBを進められない | Bは前提を失い、扱いを再判断する必要がある |
| 再浮上条件（AfterEntity） | Aの決着がつくまでBを見送る | 待つ理由がなくなり、条件を満たす |

依存先は「終了していて、不採用ではない」ときに依存を満たします。再浮上条件として待つ相手は、終了または不採用になれば条件を満たします。

## 一覧に出る状態を読む

| 用語 | 意味 |
| --- | --- |
| `surfaced` | 自身の再浮上条件を満たしている |
| active scope | 祖先Groupによって閉じられていない、現在の計画範囲 |
| `blocked` | 必要な依存先の結果を待っている |
| `orphaned` | 依存先が不採用になり、前提を失っている |
| `ready` | 採用済み・未着手で、再浮上条件、計画範囲、依存などの着手条件を満たしている |
| `terminal` | 終了または不採用である |

これらは保存した軸と関係、必要な外部条件の評価からaxonが判定します。利用者が手動で同期する必要はありません。

`triage`は、現在の計画範囲で浮上している、終了でも不採用でもない未判断や前提喪失の対象を確認する入口です。Groupに判断が必要な場合は、そのGroupを入口にして配下を一件ずつ並べないことがあります。正確な範囲は[状態モデル](../reference/state-model.md#observed-情報と-triage-frontier)に定義しています。

`ready`や`triage`に出ないことは、データが消えたことを意味しません。全件は`list`、個別の状態と待つ理由は`show <id>`で確認できます。

## IssueとGroup

Issueは一つの仕事や気づき、Groupは明示的な計画の範囲です。両方をまとめてEntityと呼び、同じ三つの軸とIDの仕組みを使います。Groupの中にはIssueや別のGroupを置けます。

Groupを開始すると、その配下が着手・判断の候補になるための範囲を開きます。実際に候補へ出るには、そのGroupが採用済みで浮上していることや、依存などの条件も満たす必要があります。子の仕事は個別に開始します。すべての子孫が終了または不採用になったら、計画全体を確認してGroupも明示的に終了します。

Groupの不採用は、子孫の状態を自動で不採用に書き換えません。配下の保存情報を保ったまま、現在の着手・判断の候補から外します。

## 決定した計画と、後から得た情報

タイトル・説明・親Group・依存先が「何をする計画か」を表します。採用・不採用を決めると、その内容は固定され、判断した計画がRevisionとして残ります。計画を変えるときは未判断に戻し、編集してから再判断します。

調査結果や作業結果、訂正、申し送りはNoteとして追記します。Noteはどの状態でも追加でき、追記によって決定済みの計画を変えることはありません。この分離により、agentへ仕事を引き継ぐときも、決めた内容と後から分かったことを区別して読めます。

正確な制約は[状態モデル](../reference/state-model.md)と[情報モデル](../reference/information-model.md)、設計の経緯や採らなかった案は[設計判断](../design/decisions.md)にまとめています。
