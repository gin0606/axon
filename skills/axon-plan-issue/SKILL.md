# Axon issue を採用済みで登録する

ユーザーがやると決めた新しい作業を、合意した内容のまま採用済み issue として登録する。

## 境界

- 新しい issue を採用済みで登録する明示的な依頼にだけ使う
- まだ採否を決めていない着想は [`axon-capture-issue`](../axon-capture-issue/SKILL.md) で扱う
- 登録後に `axon start` や実装を行うのは、別途明示的に依頼された場合だけとする

## 調査

1. 関連するコード、文書、issue を必要な範囲で読み、目的と制約を確認する。
2. `axon list` と必要に応じて `axon triage` を確認し、重複候補だけ `axon show <id>` で読む。
3. 目的、対象、完了条件が実質的に同じ未終端 issue があれば登録せず、既存 ID と判断材料をユーザーに提示する。
4. 一部が重なるだけなら登録を止めず、関連候補を最終案と一緒に提示する。依存などの関係は合意なしに設定しない。
5. 同じ作業を扱った終了済みまたは不採用の issue があれば履歴を提示し、新規作成するか既存の判断を見直すかをユーザーに確認する。

調査中は axon の状態を変更しない。

## 最終案

タイトルと description の案を作る。定型を埋めること自体を目的にせず、少なくとも「なぜ行うか」と「何を満たせば終了か」を後から読み取れるようにする。この 2 点がタイトルだけで明らかなら description は省略してよい。

対象と対象外、制約や既存の判断、依存やグループは、実装時の判断に必要な場合だけ加える。

ユーザーが登録内容を完成形として明示し、その内容で `axon plan` するよう依頼した場合は、それを確認済みの最終案として扱う。エージェントによる誤字修正や意味を変えない整形だけなら再確認しなくてよい。

エージェントが目的、対象、完了条件、分解、依存などへ実質的な判断を加えた場合は、実際に登録する最終案を提示し、ユーザーが内容と採用済みでの登録を確認するまで axon を変更しない。内容が完成していない「登録して」という依頼は、エージェントが補った内容への確認とはみなさない。

## 反映

1. `axon plan <title>` を実行する。
2. 返された ID に `axon write <id> -m <description>` で説明を書く。
3. 合意した場合だけ、依存やグループなどの構造を設定する。
4. `axon show <id>` で採用済みであること、文面、関係を確認する。
5. 作成した ID と反映内容をユーザーに報告する。

`axon plan` の成否や返された ID が不明なときは、`axon list` で作成済みか確認してから再実行する。同じ作業を推測で重複登録しない。作成後の操作だけが失敗した場合は、作成済み ID と残作業を報告し、別の issue を作らない。
